## Context

`export-review-queue` 的「清單自帶審查操作面板」設計（見 `make-export-review-self-contained`）本意是「不需要跳頁也能完成審查」，但被誤解／實作成「完全不能跳頁」，兩者不一樣。跳頁去補原料溯源資料，跟「審查動作本身要不要跳頁」是兩件事——後者維持自成一體，前者是使用者主動需要時的逃生口，不衝突。

## Goals / Non-Goals

**Goals:**
- 使用者在出口審查頁面發現資料缺漏（如原料溯源不足）時，有路徑可以去補，補完後回來繼續原本的審查操作
- 重跑審查前，若會覆蓋既有結果，讓使用者知情
- 面板顯示的 DDS 草稿內容永遠對應目前選定的市場，不會顯示舊市場的殘留內容

**Non-Goals:**
- 不撤回「清單自帶審查操作面板」的設計，審查、刪除審查、產出 DDS 草稿仍然在本頁完成
- 不做審查歷史版本紀錄（`BatchExportReview` 仍是 upsert，覆蓋確認只是提示，不是版本控制）

## Decisions

**1. 連結開新分頁（`target="_blank"`），不是原頁跳轉**

出口審查頁面通常同時展開多筆批號的面板在處理，原頁跳轉會丟失這個操作狀態（展開了哪些、選了哪個市場）。開新分頁補完資料後關掉分頁，原本的審查頁面狀態完整保留。

**2. 覆蓋確認用瀏覽器原生 `confirm()`，不做自訂 Modal**

比照專案既有慣例（`deleteOrigin()`／`removeReview()`）都用原生 `confirm()`，不為單一動作新增一套 Modal 元件。

**3. 市場切換直接清空 DDS 草稿狀態，不嘗試自動重新產出**

自動重新產出等於使用者沒點按鈕就發出一次 API 請求，且草稿產出不是免費的（要重新查 `MarketComplianceChecker`）。收起舊草稿、讓使用者看到空狀態、需要時自己再點一次「產出合規文件」，比自動觸發更符合「審查/草稿產出都是有意識操作」的既有設計哲學。

## Risks / Trade-offs

- [風險] 開新分頁補資料後，使用者若沒有手動重跑審查，出口審查頁面的舊審查結果不會自動更新 → 這是預期行為，已有 `possibly_stale` 提示會在下次載入時反映供應商文件面的變動；原料溯源本身的變動（非供應商文件）目前不在 `possibly_stale` 判斷範圍內，屬於已知限制，留待未來視需要擴充判斷條件

## Migration Plan

1. `ExportReviewsView.vue`：批號欄位、展開面板header 新增連往 `/compliance/production-batches/{id}` 的新分頁連結
2. `runReview()` 新增覆蓋確認：若該市場已有審查紀錄，跳出確認提示
3. 新增 `onPanelMarketChanged()`：切換市場時清空 `ddsOpen`/`ddsDraft`
4. 部署後以真實視覺檢查驗證：連結正確開新分頁、覆蓋確認正確跳出、切換市場後舊草稿正確收起
