# ESG·Chain 功能架構說明書

版本：v1.0　最後更新：2026-07-23

本說明書聚焦「物料—供應商—產品—批號」這條核心資料鏈的功能架構設計，記錄本輪重構後的現行邏輯，供後續開發與維護參照。系統整體定位、RBAC、法規覆蓋範圍請見《系統產品說明書》。

---

## 一、核心設計原則：四段式資料鏈

系統的永續情報建立在下列四段關係之上，彼此職責明確分工，不重疊、不繞過：

```text
① 物料 → 供應商（主/輔）
   MaterialItem ──(material_item_suppliers)──> Supplier
   每個物料登記一次核可供應商清單（主要/備用），
   所有使用此物料的產品共用，不需逐產品重複登記

② 物料類別 → 供應商合規內容標記
   MaterialGroup.required_doc_types
   物料類別決定「這類物料的供應商必須具備哪些合規文件」
   （如：棉花類 → UFLPA 聲明；木漿/橡膠類 → EUDR DDS）

③ 物料 → BOM → 產品
   MaterialItem ──(product_bom_lines)──> SalesProduct
   BOM 明細是純配方組成，不記錄「這個產品用哪家供應商」

④ 批號 → 選供應商 → 合規調查
   ProductionBatch ──(raw_material_origins.supplier_id)──> Supplier
   批次生產時才決定「這批貨的這個物料實際找誰做」，
   合規調查 = 物料合規（②必備文件類型）∩ 供應商合規（該批次實際供應商的文件狀態）
```

四段關係對應到系統的三個層級，各自只回答一個問題：

| 層級 | 資料實體 | 回答的問題 | 變動頻率 |
|---|---|---|---|
| 物料層 | `MaterialItem` / `MaterialItemSupplier` / `MaterialGroup` | 這個物料「原則上」能找哪些供應商？這類物料需要哪些合規文件？ | 低（核可清單維護後長期穩定） |
| 產品層 | `SalesProduct` / `ProductBomLine` | 這個產品由哪些物料組成？ | 中（BOM 隨 ERP 同步變動） |
| 批號層 | `ProductionBatch` / `RawMaterialOrigin` | 這一批貨的每個物料，這次實際是哪家供應商做的？ | 高（每批次可能不同） |

## 二、物料層：核可供應商清單（主/輔）

### 2.1 資料模型

`material_item_suppliers` 表：

| 欄位 | 說明 |
|---|---|
| `material_item_id` | 所屬物料 |
| `supplier_id` | 核可供應商 |
| `role` | `primary`（主要）／`alternate`（備用），每個物料僅能有一個主要供應商 |
| `source` | `erp_designated`（ERP 指定）／`manual`（人工登錄） |
| `supplier_facility_id` | 製程廠區（可選）——製程地點是「供應商＋物料」的固定屬性，不是「供應商＋特定產品」的屬性 |

### 2.2 與舊機制的關係

`bom_line_suppliers`（產品 BOM 明細層級的供應商登記）作為既有機制保留，供 PCF 計算、風險評分等既有下游邏輯繼續運作。兩者關係：

- `material_item_suppliers` 是**新的權威來源**：一個物料的核可供應商只登記一次
- 透過「套用至 BOM 明細」（`applyToBomLine`）動作，把物料核可清單寫入特定產品 BOM 行的 `bom_line_suppliers`
- 所有讀取「這個產品的上游供應商」的邏輯（`ProductUpstreamResolver`）優先採用 BOM 行已套用的 `bom_line_suppliers`，尚未套用者才退回讀取物料的核可清單

### 2.3 治理規則

- 供應商必須 `onboarding_stage = certified` 才能被列入核可清單
- 每個物料僅能有一個 `primary` 供應商，其餘為 `alternate`
- 維護入口：物料詳情頁（`/materials/items/:id`）「核可供應商清單」分頁

## 三、物料類別層：供應商合規內容標記

`MaterialGroup.required_doc_types`（如 `["UFLPA_DECLARATION", "ORIGIN_CERT"]`）標記「這個物料類別的供應商必須具備哪些合規文件」。這是連接「物料」與「供應商合規文件」的橋樑：

```text
MaterialItem → MaterialGroup → required_doc_types（必備文件類型清單）
                                        ↓
                        供應商是否具備對應 SupplierComplianceDoc
```

**已知限制**：`SupplierComplianceDoc` 目前僅以 `doc_type` 字串比對，沒有 `material_item_id`/`material_group_id` 欄位，因此無法嚴格區分「供應商 A 的 REACH 文件是為了物料 X 上傳」還是「為了物料 Y 上傳」——只要 doc_type 相符即視為滿足。此為既有限制，範圍較大，尚未在本輪修正。

## 四、產品層：物料 → BOM → 產品

`ProductBomLine` 是產品的純配方組成：

- `sales_product_id`：所屬產品
- `material_item_id`：使用的物料（可為 null，表示尚未連結物料主檔）
- `child_sales_product_id`：若此 BOM 行是另一個銷售產品的子組裝，則指向該產品（半成品串接情境）
- BOM 結構由 ERP 同步匯入，前端不可手動新增，僅能刪除個別列（商業機密考量）

BOM 明細**不記錄供應商指定**——這是本輪重構明確拿掉的部分（原本 BOM 明細表格會顯示 `primary_supplier`，現已從產品層 UI 移除，僅保留於後端 `bom_line_suppliers` 供既有計算邏輯使用）。

`ProductUpstreamResolver` 是集中式服務，統一提供「這個產品的上游供應商是誰」：

| 方法 | 用途 |
|---|---|
| `materialGroupDocTypes()` | 該產品 BOM 涉及物料類別的必備文件類型聯集 |
| `supplierIds()` | 該產品去重後的上游供應商清單（BOM 行已套用者優先，否則退回物料核可清單） |
| `supplierSummaries()` | 供「上游供應商彙總」顯示用（含物料群組、製程廠區） |
| `batchSupplierIds()` | **批次情境專用**：優先採用批次原料溯源已選定的實際供應商 |

取代原本以 `TradeGoodSupplier`（material_group 粒度、需人工逐產品登記）作為上游供應商權威來源的舊機制。

## 五、批號層：選供應商 → 合規調查

### 5.1 批次實際供應商選定

`RawMaterialOrigin`（原料溯源）是批號層「選供應商」的落地位置：

- `bom_line_id`：對應到產品 BOM 的哪一個物料行
- `supplier_id`：這一批貨、這個物料，實際是哪家供應商做的（「最後合規確認」）

前端在生產批號詳情頁新增原料溯源時：
1. 先選定「對應 BOM 物料」→ 系統帶出該物料的核可供應商清單
2. 「實際供應商」下拉限制為該核可清單內的供應商（不可任意選全部供應商），確保批次選用的供應商符合物料層已核准的資格
3. 若某物料尚未指定實際供應商，原料卡片會以紅字提示「尚未指定」

### 5.2 合規調查邏輯

`BatchExportReviewService::checkMarketDocs()` 是批號合規調查的核心：

```text
市場文件合規 = 物料合規需求 ∩ 供應商合規文件
             = MaterialGroup.required_doc_types（透過 BOM）
             ∩ SupplierComplianceDoc（該批次 batchSupplierIds() 選定的供應商）
```

**本輪修正的關鍵問題**：原本 `checkMarketDocs()` 呼叫 `ProductUpstreamResolver::supplierIds()`，取得的是**整個產品 BOM 全部上游供應商**，完全沒有讀取批次在原料溯源實際選定的供應商——等於「批號選供應商」這一步驟被合規調查邏輯繞過。修正後改用 `batchSupplierIds(batch, product)`：

- 若某 BOM 行在此批次已有選定的實際供應商（`raw_material_origins.supplier_id`），採用該供應商
- 若某 BOM 行此批次尚未選定實際供應商，才退回該行的核可供應商清單（維持向下相容，避免完全查無供應商）

同一套 `batchSupplierIds()` 也套用到批次護照（`BatchPassportService::buildComplianceDocuments()`）的合規文件顯示，確保「這個批號」看到的合規文件反映的是這批貨實際用的供應商，而非產品理論上所有可能的供應商。

### 5.3 批次護照（Batch Passport）

`BatchPassportService` 把批次涉及的產品身分、碳足跡、循環經濟、包材、有害物質、微纖維風險、製程地點、合規文件、原料溯源、出口市場審查彙總成一份唯讀 JSON 契約（`GET /production-batches/{id}/passport`），概念上對應未來可能對接的外部 DPP（Digital Product Passport）系統，v1 範圍僅供內部檢視。

## 六、前端功能入口配置

本輪重構同時調整了功能入口的分頁與導覽方式：

### 6.1 生產批號詳情頁（`/compliance/production-batches/:id`）

由單一「批號資訊」長頁拆分為 4 個分頁：

| 分頁 | 內容 |
|---|---|
| 批號資訊 | ERP 採購單號、生產日期、數量、匹配狀態、所屬產品 |
| 碳足跡與循環經濟 | 批次/產品 PCF、ISO 14067 就緒、循環經濟比例、包材資訊 |
| 有害物質揭露 | 有害物質警示、塑膠微纖維釋放風險 |
| 供應鏈合規 | 製程級地點、合規文件、原料溯源（含實際供應商選定表單） |

不再包含「出口市場審查」——該功能已完全遷出至獨立入口。

### 6.2 出口審查（`/compliance/export-reviews`，新增獨立選單項）

跨批號彙總清單，以生產批號為查詢主體（含完全未審查的批號，標示為「未審查」，避免因查詢方式只看 `batch_export_reviews` 表而漏掉待辦批號）。支援依市場／狀態／生產日期區間篩選，server-side pagination 每頁 20 筆。

清單列點擊後**展開列內面板**（非跳轉頁面），可直接執行審查、刪除審查記錄、產出 DDS 草稿、查看批次護照 JSON——生產批號詳情頁與出口審查清單頁徹底分離，互不依賴，各自透過既有 API 獨立運作。

## 七、後端服務職責分工

| 服務 | 職責 | 不做的事 |
|---|---|---|
| `ProductUpstreamResolver` | 從 BOM＋核可清單反推「產品/批次的上游供應商是誰」，四個消費者共用同一套邏輯 | 不寫入資料，純查詢反推 |
| `MarketComplianceChecker` | 商品在指定市場的合規文件比對（規則 × 供應商文件） | 不做批號情境判斷（由呼叫端透過 `supplierIdsOverride` 傳入批次範圍） |
| `BatchExportReviewService` | 批號 × 市場的出口合規審查引擎（整合文件規則、EUDR/UFLPA 溯源、DPP 欄位完整度） | 不做跨批次彙總查詢 |
| `ExportReviewQueueService` | 跨批號的出口審查清單查詢（含未審查批號） | 不執行審查本身，僅唯讀彙總 |
| `BatchPassportService` | 批次當下所有已知資料的完整彙總（唯讀 JSON 契約） | 不做「單次審查草稿」（那是 `ddsDraft()` 的職責） |
| `MaterialItemSupplierController` | 物料核可供應商清單的維護（新增/移除/主備切換/套用至 BOM 行） | 不做批次實際供應商的選定（那是 `RawMaterialOriginController` 的職責） |

## 八、已知限制與後續待辦

- `SupplierComplianceDoc` 缺少 `material_item_id`/`material_group_id` 欄位，文件與物料類別的關聯僅靠 `doc_type` 字串比對，無法嚴格區分同一供應商為不同物料上傳的同類型文件
- `process_locations`（供應鏈製程級地點）目前仍是產品層級彙總（`supplierSummaries()`），尚未比照合規文件改成批次選定供應商範圍
- `TradeGoodSupplier`／`TradeGood` model 因既有功能（`TradeGoodSupplierEmission` 等）依賴，予以保留但不再作為上游供應商權威來源，屬技術債，未來視需要再處理歷史資料清理
