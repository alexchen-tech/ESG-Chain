## 一、出口審查流程稽核修正（10 項，C1~C10）

### TC-1.1 BOM 異動即時觸發法規重算（高優先）
- **前置條件**：任一已有 BOM 的銷售產品
- **步驟**：
  1. 進「銷售產品」詳情頁，記錄目前 `inferred_regulations`
  2. 新增一筆 BOM 行，關聯的物料群組帶有法規要求（如 `EUDR_DDS`）
  3. 不重新整理，直接查看該產品的法規適用欄位
  4. 刪除剛新增的 BOM 行
- **預期結果**：新增後立即反映新法規；刪除後立即恢復原狀，不需等待排程或開啟合規儀表板頁面
- **優先級**：高

### TC-1.2 出貨關卡查詢 API（gate-check）
- **步驟**：呼叫 `GET /api/v1/production-batches/{id}/gate-check?market=EU`
- **預期結果**：回傳 `market/program/status/blocked/reviewed_at/possibly_stale/findings`；未審查過回傳 `status:"missing"`, `blocked:false`

### TC-1.3 審查結果過期提示（possibly_stale）一致性
- **步驟**：對某批次執行審查後，更新其相關供應商的合規文件（`updated_at` 變新）
- **預期結果**：`gate-check`、`dds-draft`、批次護照（`passport`）三個端點對同一筆審查記錄的 `possibly_stale` 回傳結果一致，皆為 `true`

### TC-1.4 法規範疇篩選審查
- **步驟**：對批次選定市場 EU，範疇選 DPP，執行審查；再選 CBAM，執行審查
- **預期結果**：DPP 範疇審查結果只含市場文件/PCF/DPP 相關 finding，不含 EUDR/UFLPA；CBAM 範疇只含市場文件與 PCF；不選範疇（完整審查）涵蓋全部項目

### TC-1.5 出口審查清單頁與批次詳情頁導覽
- **步驟**：在「出口審查」清單頁點擊批號連結、點擊「前往補齊溯源資料」
- **預期結果**：正確開新分頁導向生產批號詳情頁；批號詳情頁四個分頁（批號資訊/碳足跡與循環經濟/有害物質揭露/供應鏈合規）皆可正常瀏覽，且**不**出現出口審查操作項

### TC-1.6 刪除審查後清單列與展開面板同步（本輪修復的迴歸 bug）
- **步驟**：對某批次執行審查（使狀態變為警示/通過/未通過皆可）→ 展開面板點擊「✕」刪除該筆審查
- **預期結果**：清單列的市場/狀態/審查時間**同步**變回「未審查」，展開面板顯示「尚未執行過任何出口市場審查」，兩者不得互相矛盾
- **優先級**：高（此前發現過真實迴歸）

### TC-1.7 「執行審查」不帶範疇時不得 500（本輪修復的 bug）
- **步驟**：市場選 EU、範疇選「完整審查」（即不帶 program 參數），點擊「執行審查」
- **預期結果**：正常完成審查並顯示結果，不得跳出「Undefined array key "program"」錯誤
- **優先級**：高

## 二、批次製程供應商選定（batch-process-facility-selection）

### TC-2.1 製程類型清單推導
- **步驟**：進入某批次「供應鏈合規」分頁，查看「供應鏈製程級地點」區塊
- **預期結果**：僅列出該批次 BOM 涉及的核可供應商 `facility_type` 聯集（如染整、成衣製造），候選供應商僅包含 `facility_type` 相符者

### TC-2.2 選定 / 更換 / 清除製程供應商
- **步驟**：對某製程類型選定候選供應商 → 確認畫面顯示已選定 → 點擊「更換」選別的供應商 → 點擊「清除」
- **預期結果**：每步驟即時反映；清除後回到「待選定」狀態並仍列出候選清單

### TC-2.3 批次護照反映製程選定狀態
- **步驟**：選定後查看「查看完整批次護照 JSON」
- **預期結果**：`process_locations` 對應製程類型顯示 `confirmed:true` 及所選供應商/廠區資訊

## 三、製程盡職調查 SAQ 串接（process-due-diligence-saq-linkage）

### TC-3.1 已評分供應商顯示風險等級
- **前置條件**：選定的製程供應商在 `RiskAssessment` 有對應構面分數
- **步驟**：查看製程卡片
- **預期結果**：染整/濕製程/印花 顯示 `dim_e1`（環境管理）風險等級徽章；成衣縫製顯示 `dim_e3`（社會責任）風險等級徽章；徽章旁有「查看供應商評分 →」連結

### TC-3.2 未評分供應商顯示「尚未完成評分」
- **步驟**：選定一個沒有 `RiskAssessment` 紀錄的供應商
- **預期結果**：顯示灰色「尚未完成評分」，不得顯示錯誤或視為風險等級為零

### TC-3.3 風險等級不影響出口審查
- **步驟**：選定高風險等級的製程供應商後，執行該批次的出口市場審查
- **預期結果**：審查結果（status/blocked）不受製程盡職調查風險等級影響，兩者為獨立資訊維度

## 四、供應商 Portal 後端角色權限控制（supplier-portal-api-scope-enforcement）

### TC-4.1 供應商無法存取中心廠專用 API（高優先，安全性）
- **步驟**：以供應商帳號 JWT 直接呼叫 `GET /api/v1/suppliers`、`GET /api/v1/sales-products`、`GET /api/v1/export-reviews`
- **預期結果**：全部回傳 403，不得回傳資料
- **優先級**：高

### TC-4.2 供應商可正常存取 Portal 白名單路由
- **步驟**：以供應商帳號呼叫 `portal/caps`、`portal/pcf-requests`、`portal/facilities`、`auth/me` 等白名單路由
- **預期結果**：全部正常回應，功能不受影響

### TC-4.3 跨供應商資料存取阻擋（IDOR）
- **步驟**：用供應商 A 的 token 呼叫 `PUT /suppliers/{供應商B的id}/profile`、`GET /suppliers/{供應商B的id}/compliance-docs`
- **預期結果**：回傳 403，不得讀取或竄改其他供應商資料
- **優先級**：高

### TC-4.4 問卷清單強制自身供應商範圍
- **步驟**：供應商帳號呼叫 `GET /questionnaires`（不論是否帶 `supplier_id` 參數）
- **預期結果**：只回傳自己 supplier_id 的問卷，不因請求省略/竄改參數而洩漏其他供應商資料

### TC-4.5 審核動作僅限中心廠角色（本輪追加修復）
- **步驟**：供應商帳號呼叫 `POST /questionnaires/{id}/start-review`、`.../complete-review`、`.../return-review`、`.../mark-reviewed`
- **預期結果**：全部回傳 403；中心廠審核角色（admin 等）呼叫則正常執行狀態轉換
- **優先級**：中

### TC-4.6 中心廠角色不受影響（回歸測試）
- **步驟**：admin/buyer 帳號存取供應商、問卷、CAP、PCF 請求等既有中心廠功能
- **預期結果**：功能與資料完全不受本輪權限修復影響

## 五、供應商 Portal 前端 Build 拆分（supplier-portal-frontend-build-split）

### TC-5.1 兩個 Build 各自獨立
- **步驟**：分別開啟中心廠入口與供應商 Portal 入口（本機：`http://localhost:8090/` 與 `http://portal.esgchain.local:8090/`，需先於 `/etc/hosts` 加上 `127.0.0.1 portal.esgchain.local`）
- **預期結果**：頁面標題分別為「ESG·Chain」與「ESG·Chain 供應商 Portal」；供應商 bundle 不含中心廠側邊欄/頁面程式碼

### TC-5.2 深層連結不跑錯 Build（本輪修復的 bug）
- **步驟**：在供應商網域直接輸入 `portal.esgchain.local:8090/dashboard`、`/login`、`/supplier/portal` 等任意路徑
- **預期結果**：一律正確載入供應商 Portal 入口（標題「ESG·Chain 供應商 Portal」），不得跳轉成中心廠介面
- **優先級**：高（此前發現過真實迴歸：nginx 路徑改寫錯誤導致跳轉中心廠頁面）

### TC-5.3 不存在路徑不留白頁（本輪修復的 bug）
- **步驟**：在供應商網域輸入一個不存在的路徑（如殘留的 `/dashboard`）
- **預期結果**：透過兜底路由導回 `/`，依登入狀態顯示登入頁或供應商首頁，不得空白

### TC-5.4 跨角色登入互相阻擋（UX 層級，非安全邊界）
- **步驟**：供應商帳號在中心廠登入頁登入；中心廠帳號在供應商登入頁登入
- **預期結果**：皆顯示對應提示訊息並登出，不進入系統

### TC-5.5 CORS 允許供應商網域（本輪修復的 bug）
- **步驟**：從 `http://portal.esgchain.local:8090` 呼叫登入 API
- **預期結果**：CORS 預檢通過，登入請求成功，不得被瀏覽器攔截
- **優先級**：高（此前發現過真實迴歸：CORS 只允許單一來源導致登入失敗）

### TC-5.6 供應商 Portal 導覽列（本輪修復的 bug：原本完全沒有導覽 UI）
- **步驟**：登入供應商 Portal 後，從任一子頁面（如「採購需求」）操作
- **預期結果**：頂部導覽列存在且可切換：供應商入口／合規文件／採購需求／碳排申報／永續 KPI 填報／活動資料申報／CAP 矯正；含使用者名稱、角色、登出按鈕

### TC-5.7 側邊欄詳情頁高亮（AppSidebar 通用修復）
- **步驟**：中心廠介面點入任一「清單頁→詳情頁」模組（如銷售產品詳情頁）
- **預期結果**：側邊欄對應選單項目維持高亮，不因進入詳情頁（非清單頁本身路徑）而失去 active 狀態

## 七、SAQ 問卷狀態一致性

### TC-7.1 待填寫狀態標籤正確（本輪修復的 bug）
- **前置條件**：供應商有一份剛發送、尚未開始填寫的問卷（狀態 `sent`）
- **步驟**：查看供應商首頁問卷表格
- **預期結果**：狀態顯示「待填寫」，不得顯示英文原始字串 `sent`

### TC-7.2 退回重新提交完整生命週期
- **步驟**：中心廠審核人員將某問卷退回（`return-review` 附退回原因）→ 供應商查看「已退回」提示與原因 → 修改後重新提交
- **預期結果**：狀態依序 `under_review → review_returned →`（供應商編輯提交）`→ submitted`；中心廠端可見狀態變化並可重新「開始審核」

## 八、永續 KPI / 揭露資料一致性

### TC-8.1 中心廠端分組標題正確（本輪修復的 bug）
- **步驟**：進入供應商詳情頁「永續績效」分頁

### TC-8.3 KPI 填報 API 白名單與資料範圍
- **步驟**：供應商呼叫 `GET/POST portal/disclosures`
- **預期結果**：正常運作且僅回傳/寫入自己供應商的資料
